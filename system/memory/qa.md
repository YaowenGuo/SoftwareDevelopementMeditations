# 问题分析

## Android 15 强制使用 16K 页面，为什么16K页面能提升性能？

Armv8‑A (AArch64) 支持编译时选择 4K / 16K / 64K Granule。

使用 16 K 页面的原因是当前首页的 RAM 越来越大，而且应用的程序也越来越大，占用内存越来越多。64位设备支持16KB内存页面，主要是为了顺应现代硬件发展趋势，并解决4KB页面在大内存设备上暴露出的性能瓶颈。但页面大小是一个全局折中：

1. TLB (Translation Lookaside Buffer 页表缓存)

虚拟地址通过页表转换为物理地址，更大的物理也让页表数量减少，页表的层级也减少。

4K：4 级 (9+9+9+9+12=48)
16K：3 级 (11+11+12+14≈48)
64K：64K 仍是 3 级

随着页增大：

收益:
- 减少 TLB miss：页面增大页目录减少意味着，在地址转换时TLB 覆盖（TLB reach）增高、TLB的命中增高。

- 页目录减少页表本身占据的内存减少、让页表层级减少、页表内存开销大。

- 页表层级减少能降低 page walk 次数（既因为 miss 数少，也因为单次 walk 层数少），能耗下降。

- 一次申请更大也页，减少 Page Fault 次数。

损耗：
- 页增大的同时也带来浪费，内部碎片（internal fragmentation 页面内部无法使用的部分）上升：小对象/小文件尾部浪费。

- 加载和写入数据是按照整页作为一个整体，导致I/O 粒度增大、写放大。

- COW（写时复制）和细粒度保护粒度变粗，潜在额外开销。

16K 介于 4K 与 64K 之间，在多数 Android 典型工作负载（大型 App、浏览器、游戏、相机/多媒体、AI 推理）中，往往能取得“明显增益 + 可接受碎片”的折中。

与 THP 相比：16K 是“稳定平均收益”策略，不依赖运行时合成大页成功率。与 64K 相比：在碎片、兼容性、I/O 细粒度方面代价更可控。选择 16K 是整体性能的折中选择。
