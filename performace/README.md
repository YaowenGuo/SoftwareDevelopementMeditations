# 性能

性能的本质资源利用率与执行效率：

- **CPU 饱满度**： 减少阻塞（IO、同步锁、系统调用）。

    - **无法并行**：Amdahl's Law (阿姆达尔定律)： 程序中不可并行的串行部分，决定了你性能优化的上限。本质补充：高性能不仅关乎单核的快慢，更关乎在核数增加时，性能是否能 线性增长。一旦有 IO 或者死锁等，导致 CPU 处于无代码可执行，从而进入空等待状态。无法最大化利用CPU 性能。现代高性能系统普遍采用异步 I/O、事件驱动模型，让 CPU 始终在处理可推进的任务。
    - 死锁，但更常见的是锁争用：多个线程频繁争夺同一把锁，导致大量线程被挂起/唤醒（上下文切换），甚至线程饥饿。上下文切换的成本：切换一次约 1-10 微秒（取决于系统），但更重要的是污染 CPU 缓存/L1/L2，切换回来的工作会慢很多。
    
    - 负载均衡：某个核心满荷，其余空闲，整体吞吐受限。

    - 无锁结构、细粒度锁、工作窃取 等减少串行等待。

    - 隐式的资源争用: 内存分配器（malloc/free）在竞争频繁时的锁、碎片、系统调用。垃圾收集器（GC）的停顿与扫描成本。内核中的锁、中断平衡、网络协议栈处理。这些通常不由业务代码直接控制，但理解它们对极致性能调优至关重要。

- **执行效率**： 减少冗余（重复计算、无用逻辑、UI 过度绘制）。重复的代码执行，或者无用的代码被执行。
    - **无用的循环**：浪费 CPU 计算资源，例如 `while (flag == 0) {}`,`for(i=0;i<large_num;i++){;}）`。

    - **自旋型原语** ：atomic_flag_test_and_set 循环、std::atomic<T>::wait() 的某些实现（可以忙等一短暂时间后让出）、自旋锁 — 忙等期间占用 CPU。

    - **并发切换**：程序的执行太碎片，频繁I/O层系统系统调用，虽然 CPU 在运行，但大部分时间花在了上下文切换（Context Switch）和争夺信号量上，这属于极大的损耗。减少不必要的控制权转移（系统调用、中断、上下文切换）。

    - **重复执行**：特别是在 UI 系统中，由于刷新信号的周期性到来。放大了无效代码的执行次数。 UI 和周期性任务里非常常见，如未去抖的刷新、无效的重绘、无意义的重复计算。 在不该执行的时机、以不必要频率触发了昂贵逻辑。



- **算法效率**： 优化算法（降低复杂度、空间换时间）
    
    大多数性能热点可以用更合适的数据结构和算法来优化。比如从 ArrayList 的 contains O(n) 换成 HashSet O(1) 在百万级数据下天壤之别。


- **数据亲和性**： 优化缓存利用，减少内存搬运和 GC 频率。减少 CPU 因错误共享、缓存缺失而停滞的“虚假忙碌”。
    1. 内存与缓存层次结构 (Memory & Cache Locality)
    现代 CPU 的瓶颈往往不在执行单元，而在 数据供给。
    即使算法复杂度低，如果访存模式造成大量 cache miss、TLB miss、缺页，性能可能比“笨算法但 cache 友好”的实现差一个数量级。
    CPU 缓存未命中 是比“CPU 空转”更隐蔽、更频繁的性能杀手。一次 L3 缓存未命中可能消耗几百个 CPU 周期，而一次算术运算仅需 1-2 周期。
    数据结构的内存布局：比如链表的遍历会频繁造成缓存缺失，而紧凑的数组（std::vector / List of structs）更优。

    - 在现代计算机中，CPU 往往不是被“逻辑”卡住的，而是被“等数据”卡住的。
    
    - 缓存命中率： 哪怕 CPU 没在等待 IO 或死锁，如果它频繁地发生 Cache Miss（缓存未命中），被迫从主存（RAM）读取数据，其性能会下降数百倍。
    结构布局（AoS vs SoA）、遍历顺序、预取策略、对齐等直接影响性能。这属于“最大化有效利用 CPU”的延伸，但足够重要，值得单独列为一条。

    - 伪共享 (False Sharing)： 在多核架构下，不同线程操作同一个 Cache Line 的不同变量，会导致频繁的缓存失效，导致核间缓存同步开销。
    本质补充： 优秀的程序不仅要最大化利用 CPU 频率，还要最大化利用 CPU 缓存的局部性。
    
    2. 数据的“搬运”成本 (Data Marshalling & Latency)
    有时候代码写得很精简，算法也是，但程序依然慢。
    序列化与反序列化： 在微服务或跨进程通信中，数据转换的开销往往大于业务逻辑本身。
    内存拷贝： 频繁的 memcpy 或不必要的对象创建（导致频繁的 GC 压力）是隐藏的性能杀手。
    本质补充： 性能优化很多时候是在减少 不必要的数据移动。
    
    缓存行对齐、预取、顺序访问、避免内存屏障等。

- **并发质量**： 降低锁粒度，减少上下文切换，提高吞吐量。
    导致吞吐高但延迟差。
    延迟、吞吐与抖动的权衡（Tail Latency / QoS）
    有时“最大化 CPU 利用”会带来长尾延迟和不可预测的响应时间。
    实时系统、金融交易、线上服务更关注 P99 延迟、调度抖动，而不是平均 CPU 利用率。
    这引申出调度策略、优先级反转、隔离、NUMA 亲和性等，是更高阶的性能维度。

- 高效IO: 
    现代系统可以通过 非阻塞 I/O + 多路复用（epoll/io_uring）让一个线程控制上千连接，避免创建大量阻塞线程。
    磁盘 I/O 比网络 I/O 更慢，但更多人忽略了小文件随机读比大文件顺序读低几个数量级。

5. 编译器与运行时优化能力（以及它们的失效条件）
    编译器优化（内联、向量化、常量传播、尾调用）对性能影响巨大，但很容易被不经意破坏，比如：

    过于复杂的指针别名导致无法向量化。

    虚函数调用阻止内联。

    异常处理、范围检查、过度的模板实例化导致代码膨胀和指令缓存压力。
    优化不止在源码，还在 生成指令的质量。

    分支预测失败：现代 CPU 40% 以上的性能损失可能来自错误预测的跳转（如循环内难以预测的 if）。

    编译器自动向量化（SIMD）未启用或未生效，导致循环效率低。

    虚函数调用（尤其是热路径中的动态分发）阻止内联和优化。


优化方向：
CPU 饱满度： 减少阻塞（IO、同步锁、系统调用），并行执行。
执行有效性： 减少冗余（重复计算、无用逻辑、UI 过度绘制）。
计算科学性： 优化时间和空间复杂度。
数据亲和性（补充）： 优化缓存利用，减少内存搬运和 GC 频率。
并发质量（补充）： 降低锁粒度，减少上下文切换，提高吞吐量。

作为性能专家，我完全赞同你的框架，但为了让这个理论更完整，我建议从以下三个维度进行补充，这也是现代高性能编程中最具挑战性的部分。

- 性能的终极本质是 “用最少的时间与资源完成指定工作”，而这条路径上，计算、访存、通信、同步、调度都可以成为瓶颈。你已有的思维框架，加上这些补充，能帮你更系统地分析和优化任何程序。

- 测量驱动的反馈闭环（Profiling & Observability）：识别哪里是性能瓶颈至关重要。能否快速定位热点？性能工作往往失败于“猜测优化点”。能否区分是 CPU bound，内存 bound 还是 I/O bound？现代工具链（perf, eBPF, flamegraph, PMU 计数器）允许从微架构层面分析停顿，这对定性和定量的决策至关重要。不要凭直觉优化，而要用数据说话。95% 的执行时间往往集中在 5% 的代码中（二八定律）。没有性能剖析（火焰图、采样、埋点），优化东墙可能拆了西墙。


Other(归类到哪里？):
虚假唤醒、ABA 问题 等并发陷阱也会降低有效吞吐。
在 GC（垃圾回收）语言（Java/C#/Go）中，对象分配速率 决定了 GC 停顿的频率和时长。例如在 UI 每帧创建大量临时对象会引发频繁的 minor GC，导致掉帧。
对象池、栈上分配（struct/value type）、复用缓冲区 是常见优化手段。
