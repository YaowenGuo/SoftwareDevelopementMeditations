# 副作用函数

理解这一点很重要：Composable 函数跟其它声明式 UI 的 ，在整个生命周期内会被执行 0 次或多次。有一些操作在 Composable 函数中，但是不想在每次调用时都执行。例如弹窗、导航。

下面是 Compose 中主要的副作用函数及其使用场景：

| 副作用函数 | 执行时机与特点 | 主要使用场景 |
| :--- | :--- | :--- |
| **`LaunchedEffect`** | 在可组合项**首次进入组合时**启动协程，当它**离开组合或指定的 `key` 发生变化时**，协程会被取消并重新启动。 | 执行与可组合项生命周期绑定的**挂起函数**，如：<br>- 动画驱动<br>- 一次性异步任务（如网络请求）<br>- 对数据流（Flow）进行收集 |
| **`DisposableEffect`** | 在可组合项**进入组合时**执行，并**必须**在 `onDispose` 块中定义清理逻辑。当 `key` 变化或可组合项离开组合时，会先执行 `onDispose` 进行清理，然后重新执行。 | 执行需要**配对进行初始化和清理**的操作，防止内存泄漏：<br>- 注册/取消注册监听器或回调<br>- 开始/停止数据上报或传感器监听<br>- 管理需要释放的资源 |
| **`SideEffect`** | 在**每次成功重组（recomposition）并提交到界面之后**同步执行。 | 将 Compose 状态**同步到非 Compose 环境**：<br>- 更新系统UI（如状态栏颜色）<br>- 与外部分析SDK同步数据<br>（注意：不适用于耗时或只需执行一次的操作） |
| **`rememberCoroutineScope`** | 返回一个**与可组合项生命周期绑定的协程作用域**（`CoroutineScope`）。 | 在**非协程上下文**（如按钮点击回调）中**手动启动协程**。 |
| **`rememberUpdatedState`** | 在不重启 `LaunchedEffect` 等效果的前提下，**记住并更新对最新值的引用**。 | 在 `LaunchedEffect` 或 `DisposableEffect` 内部，需要**使用一个会变化的值，但又不希望因该值变化而重启效果**。 |
| **`produceState`** | 启动一个协程，并将发射的值**转换为 Compose 的 `State`** 对象。 | 将**非 Compose 状态（如外部数据流）转换为可被 Compose UI 观察的 `State`**。 |
| **`snapshotFlow`** | 将 Compose 的 `State` 对象**转换为一个数据流（Flow）**。 | 在协程中**观察 Compose 状态的变化**，并执行副作用，如：<br>- 在状态变化时进行上报 |
| **`derivedStateOf`** | 根据一个或多个状态，**计算并派生出新的状态**。仅当计算结果发生变化时，才会触发重组。 | **优化重组性能**，避免因上游状态频繁变化而导致不必要的重组。 |

**使用建议**：
- **理解生命周期**：关键在于理解每个 API 与 Compose 生命周期（进入/离开组合、重组）的绑定关系。
- **优先使用内置 API**：对于上述场景，应优先使用 Compose 提供的 Effect API，而不是手动管理，以确保行为的可预测性。
- **注意 `key` 的使用**：`LaunchedEffect` 和 `DisposableEffect` 的 `key` 是控制其重启的关键，应谨慎选择。
- **避免过度使用**：副作用 API 用途广泛，但需确保其中的操作与 UI 相关，并维护单向数据流，避免滥用。

## 状态的生命周期

 rememberSaveable 使用 Bundle 来存储 UI 状态，而这个 Bundle 也被其他写入它的 API 共享，比如你 Activity 中的 onSaveInstanceState() 调用。然而，这个 Bundle
  的大小是有限的，存储大对象可能会在运行时导致 TransactionTooLarge 异常。在单 Activity 的 App 中这尤其成问题，因为整个 App 共用同一个 Bundle。

  为避免这类崩溃，你不应该在 bundle 中存储庞大复杂的对象或对象列表。

  相反，应该只存储所需的最小状态（如 ID 或 key），然后用它们把恢复更复杂 UI 状态的工作委托给其他机制，例如持久化存储（persistent storage）。

  ▎ 注意：在某些情况下，不存储所有 UI 元素的状态也是可以接受的。这些设计选择取决于你 App 的具体用例以及用户期望它如何表现。

  验证状态恢复（Verify state restoration）

  你可以验证用 rememberSaveable 存储在 Compose 元素中的状态，在 Activity 或进程重建时是否被正确恢复。有专门的 API 可以做到这一点，例如
  StateRestorationTester。详见《Testing》文档。

然而，ViewModel 实例无法在系统发起的进程终止中存活。要让 UI 状态在这种情况下也能存活，请使用 ViewModel 的 Saved State 模块，它包含 SavedStateHandle API。

  最佳实践

  SavedStateHandle 同样使用 Bundle 机制来存储 UI 状态，因此你应该只用它来存储简单的 UI 元素状态。

屏幕 UI 状态（Screen UI state）——通过应用业务规则、访问 UI 之外的其他层而生成的状态——由于其潜在的复杂性和大小，不应存储在 SavedStateHandle
  中。你可以使用其他机制（如本地持久化存储）来存储复杂或大量的数据。进程重建后，屏幕会用 SavedStateHandle 中恢复的瞬时状态（如果有的话）重新创建，而屏幕 UI
  状态则会再次从数据层生成。


  总结（Summary）

  下表总结了本节涉及的 API，以及何时使用每个 API 来保存 UI 状态：

  ┌────────────────────┬──────────────────┬────────────────────────┐
  │        事件        │     UI 逻辑      │ ViewModel 中的业务逻辑 │
  ├────────────────────┼──────────────────┼────────────────────────┤
  │ 配置变更           │ rememberSaveable │ 自动（Automatic）      │
  ├────────────────────┼──────────────────┼────────────────────────┤
  │ 系统发起的进程终止 │ rememberSaveable │ SavedStateHandle       │
  └────────────────────┴──────────────────┴────────────────────────┘

  使用哪个 API 取决于状态保存在何处以及它所需的逻辑。对于用于 UI 逻辑的状态，使用 rememberSaveable。对于用于业务逻辑的状态，如果你把它保存在 ViewModel 中，就用
  SavedStateHandle 来保存它。

  你应该使用 bundle 类 API（rememberSaveable 和 SavedStateHandle）来存储少量的 UI 状态。这些数据是把 UI 恢复到先前状态所需的最小数据，再配合其他存储机制使用。例如，如果你在
  bundle 中存储了用户正在查看的个人资料的 ID，你就可以从数据层去获取像资料详情这样的庞大数据。

  ▎ 关于保存 UI 状态的不同方式，更多信息见通用的《Saving UI State》文档和架构指南的数据层（data layer）页面。

  ---
  核心要点一句话：UI 逻辑用的状态 → rememberSaveable（存 Bundle，跟随 Composition）；业务逻辑用、提升到 ViewModel 的状态 → 配置变更靠 ViewModel 自动保留，进程终止靠
  SavedStateHandle。两者都只存最小必要状态（ID/key），大数据交给持久化存储。、



  在 Compose 中，有几个函数可用于在组合期间及之后持久化状态：remember、retain、rememberSaveable 和
  rememberSerializable。它们在生命周期和语义上各不相同，各自适用于存储特定种类的状态。区别如下表：

  rememberSaveable 和 rememberSerializable 构建在 remember
  之上。它们在本指南讨论的记忆化函数中生命周期最长。除了在重组间对对象进行位置记忆化外，它还能**保存（save）**值，使其能在 Activity
  重建（包括配置变更和进程终止）后被恢复。（进程终止是指系统在 App 进程处于后台时将其杀死，通常是为前台 App 释放内存，或用户在 App 运行时撤销了其权限。）

  rememberSerializable 的工作方式与 rememberSaveable 相同，但能自动支持持久化那些可用 kotlinx.serialization 库序列化的复杂类型。如果你的类型已（或可以）被标记为
  @Serializable，就选 rememberSerializable；其他所有情况都用 rememberSaveable。

  这使得 rememberSaveable 和 rememberSerializable
  成为存储与用户输入相关状态的完美候选，包括文本框输入、滚动位置、开关状态等。你应该保存这些状态以确保用户永远不会丢失他们所在的位置。一般而言，对于 App
  无法从其他持久化数据源（如数据库）检索到的任何状态，你都应该用 rememberSaveable 或 rememberSerializable 来记忆化。

- 你记忆化的值必须能由以下一个或多个数据类型表示：基本类型（包括 Int、Long、Float、Double）、String，或这些类型的数组。
  - 当一个被保存的值被恢复时，它会是一个新实例，与组合之前使用的实例相等（==）但不是同一引用（===）。


retain API 在记忆化时长上介于 remember 和 rememberSaveable / rememberSerializable 之间。它之所以名字不同，是因为被 retain 的值还会经历与被 remember 的值不同的生命周期。

  当一个值被 retain（保留）时，它既被位置记忆化，又被保存在一个有独立生命周期、绑定到 App 生命周期的次级数据结构中。被 retain
  的值能在不被序列化的情况下存活过配置变更，但无法在进程终止后存活。如果组合层级被重新创建后该值未被使用，被 retain 的值会被 retire（退役）（这是 retain
  中相当于"被遗忘"的概念）。

  作为生命周期比 rememberSaveable 短的交换，retain 能持久化那些无法序列化的值，如 lambda 表达式、flow，以及位图（bitmap）这样的大对象。例如，你可以用 retain
  来管理媒体播放器（如 ExoPlayer），以防止配置变更期间媒体播放被打断。


 retain 与 ViewModel 对比

  在核心上，retain 和 ViewModel 在其最常用的能力——跨配置变更持久化对象实例——上提供了类似的功能。选择 retain 还是
  ViewModel，取决于你要持久化的值的类型、它应该如何被限定作用域，以及你是否需要额外功能。

  ViewModel 是通常封装 App 的 UI 层与数据层之间通信的对象。它们让你能把逻辑移出 composable 函数，从而提升可测试性。ViewModel 在 ViewModelStore 中作为单例被管理，其生命周期与被
  retain 的值不同。ViewModel 会一直保持活跃直到其 ViewModelStore 被销毁，而被 retain 的值则在内容被永久从组合中移除时退役（以配置变更为例，这意味着如果 UI
  层级被重建、且重建后被 retain 的值未被消费，该值就会退役）。

  ViewModel 还包含开箱即用的集成：与 Dagger 和 Hilt 的依赖注入、与 SavedState 的集成、以及用于启动后台任务的内置协程支持。这使 ViewModel
  成为启动后台任务和网络请求、与项目中其他数据源交互的理想场所，并可选地捕获和持久化那些既应在 ViewModel 中跨配置变更保留、又应在进程终止后存活的关键 UI 状态。

  retain 最适合作用域限定于特定 composable 实例、且不需要在兄弟 composable 间复用或共享的对象。ViewModel 是存储 UI 状态和执行后台任务的好地方，而 retain 则适合存储 UI
  管线类对象，如缓存、曝光追踪和分析、对 AndroidView 的依赖，以及其他与 Android 操作系统交互或管理第三方库（如支付处理器或广告）的对象。

  对于设计 Modern Android app architecture 推荐之外的自定义架构模式的高级用户：retain 也可用于构建一个自研的"类 ViewModel" API。虽然不提供开箱即用的协程和 saved-state 支持，但
  retain 可作为这类"ViewModel 仿制品"生命周期的构建基块，在其上再构建这些功能。如何设计此类组件的细节超出本指南范围。
