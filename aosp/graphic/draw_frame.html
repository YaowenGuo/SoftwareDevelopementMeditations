View 内容如何最终绘制到屏幕：从 ViewRootImpl 到 SurfaceFlinger

先澄清一个概念：View 的内容并不是画到 ViewRootImpl 本身上。 ViewRootImpl 不存像素，它负责调度绘制并持有窗口的 Surface。 View 的内容最终写进这个 Surface 背后的图形缓冲区（GraphicBuffer）， 再由 SurfaceFlinger 合成后显示到屏幕上。
目录
  1. 准备阶段：ViewRootImpl 拿到 Surface
  2. 触发绘制：invalidate → VSYNC → performTraversals
  3. 硬件加速路径（默认）
  4. 软件绘制路径
  5. 从 Buffer 到屏幕
  6. 总结

1. 准备阶段：ViewRootImpl 拿到 Surface

WindowManagerGlobal.addView()
  └─ new ViewRootImpl()
  └─ ViewRootImpl.setView(decorView)
        ├─ requestLayout()                  // 先安排一次遍历
        └─ mWindowSession.addToDisplay()    // Binder → WMS，注册窗口

第一次 performTraversals() 时会调用 relayoutWindow()：

ViewRootImpl.relayoutWindow()
  └─ mWindowSession.relayout(..., mSurfaceControl)
  │     // WMS 创建 SurfaceControl（对应 SurfaceFlinger 中的 Layer）
  └─ Android 12+：
        mBlastBufferQueue = new BLASTBufferQueue(mSurfaceControl, ...)
        mSurface.transferFrom(mBlastBufferQueue.createSurface())

这一步之后，ViewRootImpl 的 mSurface 才是有效的。 它是 BufferQueue 的生产者端，往里画的东西最终会交给 SurfaceFlinger。

2. 触发绘制：invalidate → VSYNC → performTraversals

View.invalidate()
  └─ 沿 mParent 链向上 invalidateChild / onDescendantInvalidated
       └─ ViewRootImpl.scheduleTraversals()
            ├─ 发送同步屏障（postSyncBarrier），优先处理异步消息
            └─ Choreographer.postCallback(CALLBACK_TRAVERSAL, mTraversalRunnable)
                 └─ 等下一个 VSYNC
                      └─ doTraversal() → performTraversals()
                           ├─ performMeasure()
                           ├─ performLayout()
                           └─ performDraw() → draw(fullRedrawNeeded)

在 ViewRootImpl.draw() 里分成两条路径：

if (isHardwareEnabled()) {
    mAttachInfo.mThreadedRenderer.draw(mView, mAttachInfo, this);   // 硬件加速（默认）
} else {
    drawSoftware(surface, mAttachInfo, xoff, yoff, ...);            // 软件绘制
}

3. 硬件加速路径（默认）

这条路径分两段：UI 线程只录制绘制命令，RenderThread 负责真正渲染。

3.1 UI 线程：构建 DisplayList（RenderNode 树）

ThreadedRenderer.draw()
  └─ updateRootDisplayList(view)
       └─ updateViewTreeDisplayList(view)
            └─ view.updateDisplayListIfDirty()        // 只重建脏的 View
                 ├─ RecordingCanvas canvas = renderNode.beginRecording(w, h)
                 ├─ draw(canvas)  或  dispatchDraw(canvas)（自身无需绘制时走快速路径）
                 └─ renderNode.endRecording()          // 生成 DisplayList
       └─ rootCanvas.drawRenderNode(view.updateDisplayListIfDirty())

View.draw(Canvas) 的标准步骤：

步骤方法作用
1drawBackground()绘制背景
2saveLayer（必要时）为渐变边缘做准备
3onDraw(canvas)绘制自身内容
4dispatchDraw(canvas)绘制子 View
5绘制渐变边缘 + restoreFading edges
6onDrawForeground()前景、滚动条
7drawDefaultFocusHighlight()默认焦点高亮

ViewGroup.dispatchDraw() 对每个子 View 调用 drawChild()， 也就是 child.draw(canvas, this, drawingTime) 这个三参数版本。 在硬件模式下它不会直接画像素，而是：

RenderNode rn = child.updateDisplayListIfDirty();
((RecordingCanvas) canvas).drawRenderNode(rn);

所以整个 View 树会变成一棵 RenderNode 树：父节点的 DisplayList 中只记录一条 “绘制子 RenderNode”的操作。translationX、alpha、rotation 等属性直接存在 RenderNode 上，修改这些属性不需要重新录制，这也是属性动画高效的原因。

onDraw 里调用的 canvas.drawRect()、drawText() 等， 在这一阶段只是被记录为操作，并没有产生任何像素。

3.2 同步到 RenderThread

ThreadedRenderer.syncAndDrawFrame(frameInfo)
  └─ JNI → RenderProxy::syncAndDrawFrame()
       └─ DrawFrameTask::drawFrame()     // 投递到 RenderThread，UI 线程阻塞等待 sync 完成

RenderThread 中的流程：

DrawFrameTask::run()
  ├─ syncFrameState()        // 把 UI 线程的 RenderNode 属性 / DisplayList 同步到渲染侧，上传 Bitmap 纹理
  │    （同步完成后即唤醒 UI 线程，UI 线程可以去处理下一帧）
  └─ CanvasContext::draw()
       ├─ mRenderPipeline->getFrame()       // 向 Surface dequeueBuffer，拿到一块 GraphicBuffer
       ├─ mRenderPipeline->draw(...)        // SkiaOpenGLPipeline / SkiaVulkanPipeline
       │     └─ 遍历 RenderNode 树，回放 DisplayList → Skia → GPU 指令
       └─ mRenderPipeline->swapBuffers()    // eglSwapBuffers / vkQueuePresent
             └─ Surface::queueBuffer()      // 把画好的 buffer 还给 BufferQueue

到这里，View 的内容才真正变成像素，存在一块 GraphicBuffer 里。

4. 软件绘制路径

关闭硬件加速时，直接由 CPU 通过 Skia 画进 buffer：

// ViewRootImpl.drawSoftware()
Canvas canvas = mSurface.lockCanvas(dirty);   // dequeueBuffer 并把 buffer 包装成 Bitmap-backed Canvas
mView.draw(canvas);                           // 整棵树同步地直接画像素
surface.unlockCanvasAndPost(canvas);          // queueBuffer

和硬件路径相比，这里没有 DisplayList 和 RenderThread，全部在 UI 线程完成。

硬件加速软件绘制
Canvas 类型RecordingCanvas（只录制）Bitmap-backed Canvas（直接出像素）
光栅化执行者RenderThread + GPUUI 线程 + CPU
局部刷新只重建脏 View 的 DisplayList按 dirty 区域重绘整棵树相交部分
属性动画改 RenderNode 属性，无需重录需要重绘

5. 从 Buffer 到屏幕

queueBuffer
  └─ BLASTBufferQueue（Android 12+，在 App 进程内）
       └─ 通过 SurfaceControl.Transaction 把 buffer 提交给 SurfaceFlinger
            └─ SurfaceFlinger 在 VSYNC-sf 时刻收集所有 Layer
                 └─ 交给 HWC（Hardware Composer）合成；
                    HWC 处理不了的部分由 GPU 合成（Client Composition）
                      └─ 送显（Display）

Android 12 之前，BufferQueue 的消费者端在 SurfaceFlinger 进程里。 12 及以后改为 BLAST，buffer 和窗口几何变化可以放在同一个 Transaction 里原子提交。

6. 总结

View.invalidate()
   ↓
ViewRootImpl.scheduleTraversals() ──(Choreographer, VSYNC)──→ performTraversals()
   ↓                                                       measure / layout / draw
ViewRootImpl.draw()
   ├─ 硬件：ThreadedRenderer.draw()
   │     UI 线程：View.draw(RecordingCanvas) → 录制 DisplayList（RenderNode 树）
   │     RenderThread：sync → dequeueBuffer → Skia/GPU 回放 → queueBuffer
   └─ 软件：Surface.lockCanvas → View.draw(Canvas) → unlockCanvasAndPost
   ↓
Surface（BufferQueue / BLASTBufferQueue）中的 GraphicBuffer
   ↓
SurfaceFlinger + HWC 合成 → 屏幕
一句话概括：ViewRootImpl 负责调度绘制并提供 Surface； View 在硬件加速下把绘制操作录制成 RenderNode，由 RenderThread 用 GPU 画进 Surface 的缓冲区； 最后由 SurfaceFlinger 把各窗口的 buffer 合成后显示到屏幕。
