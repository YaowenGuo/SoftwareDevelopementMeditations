# 图形显示系统


图形系统作为用户最重要交互端口，如果是一个非计算机人员，一个直观的感觉是桌面就是整个操作系统——或者至少是整个系统最核心的部分。但任何一本操作系统教科书都会说，操作系统的核心是：
- 进程调度
- 进程间通信
- 内存管理
- 虚拟文件系统
- 网络堆栈

图形系统虽然复杂，但在内核中的部分极少。因此图形系统的架构堆栈大部分在应用层——除了两类会抢占的资源——硬件资源的管理（显示器、GPU）、计算任务的调度（绘制逻辑，绘制内容）。这很好理解，内核只处理资源的管理，需要仲裁谁能使用硬件资源。除此之外的所有内容都应该尽量留在应用层。


看一下显示屏上的显示，它不能只显示一个程序（早期终端界面真的就是一个程序）。首先注意的是桌面，桌面可以和应用程序的窗口重叠、多个应用程序的窗口可以在整个屏幕上任意排列，层叠。这就引入一个新的问题 —— 系统的程序运行单位是进程，而进程是相互隔离的，每个进程想要显示的画面都在自己隔离的进程中执行和提交申请，根本不清楚别的进程绘制的内容。——谁负责将这些应用的窗口（一个程序可以有多个窗口，例如浏览器多个标签可以独立出来）排列呢？到底哪个窗口应该在前，哪个在后？窗口应该绘制在什么位置？有写窗口信息还可以和桌面融合，例如 MacOS 的顶部栏可以显示应用的菜单。

这个工作并不是各个进程自己负责的，他们只是请求一个绘制空间 —— 这在各个图形系统上被抽象为窗口 —— 进程绘制在这个窗口上就结束了。具体这个窗口排放位置和堆叠关系，很明显，需要有一个负责将各个进程的窗口合成成一帧最终画面，提交给内核管理的硬件的程序。一个应用给其它应用提供窗口管理和和合成服务——也就是 C/S 架构。


聚焦于窗口管理和合成服务。它需要完成：

- 窗口管理：都有哪些软件创建了那些窗口，位置、层叠关系、谁获得焦点。进程之间互相看不见，只有一个站在所有进程之上的角色，才能掌握全局的窗口信息，并做出“谁在前、谁在后、谁接收输入”的裁决。这份裁决是**策略**，它随用户操作、应用切换、分屏等场景不断变化，所以它应该留在应用层，由一个可以随时调整规则的服务来决定，而不是写死在内核里。
- 画面合成：每个进程只把内容画在自己的缓冲区里，互不知晓。要得到屏幕上那一帧，必须把这些缓冲区按窗口管理给出的位置和层叠关系叠加（包括裁剪、缩放、透明混合）成一张完整的图。这件事必须集中做一次：如果各进程自己往屏幕上写，就会互相覆盖、画面撕裂，也无法保证被遮挡部分不被画出来。合成需要的是“读取所有进程的缓冲区”，这个权限只能由一个统一的服务持有。
- 显示提交与刷新节奏：合成好的画面最终要交给显示硬件，而显示器按固定频率刷新（VSYNC）。如果提交的时机和刷新不同步，就会出现撕裂或卡顿。同时，叠加这类工作既可以让 GPU 做，也可以让显示硬件直接做（更省电），但具体能做什么取决于厂商的硬件。所以需要一层贴近硬件的抽象，向上屏蔽硬件差异，向下掌握刷新节奏，并回答“这些图层，硬件能自己叠加吗”。

在安卓上，这三个职责没有被设计成一个程序，而是由三个进程协作完成。
    - SystemServer 的 WindowManagerService 服务。:管窗口的位置、层级、焦点。WMS 放在 SystemServer 中是因为 AMS 也在这个进程中，和 AMS 有甚多内容
    - SurfaceFlinger 进程 —— 合成决策者与最终提交者
    - HWC (Hardware Composer HAL) —— 硬件合成顾问与执行者

图形应用则扮演一个客户端。甚至连桌面都是一个应用，只不过多了一些管理其它应用的权限，可以显示其它应用的入口，以及启动其它应用。

## WMS

首先聚焦 WMS。程序想要绘制图形，首相就是要申请窗口。这个动作在程序的主线程完成。











窗口管理是任何一个 UI 桌面的最主要部分，它将进程抽象为一个显示窗口，显示在屏幕上。
